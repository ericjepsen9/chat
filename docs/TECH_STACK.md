# 重写版技术栈

本文档记录项目重写时确定的技术栈、第一版范围和开发规范。

## 背景与约束

- **端到端加密（E2EE）是产品的核心卖点**
- 用户主要在中国大陆，服务器部署在境外（香港或日本）
- 主打网页端，之后提供安卓 App 和 iOS App
- 登录以邮箱验证码为主，短信验证码为辅
- **一个人开发，使用 Claude Code**

由此得出三条原则：

1. **加密协议不自己实现**，使用成熟、经过审计的方案
2. **能用现成的就不自己做，能少运维就少运维**
3. **第一版只做最核心的功能**

## 核心决策：基于 Matrix 协议

聊天和通话基于 [Matrix](https://matrix.org) 协议构建：服务端部署 Matrix homeserver，客户端使用 Matrix 官方 SDK，界面自己开发。

Matrix 已经实现并经过安全审计的部分，**我们不再自己做**：

| 能力 | 说明 |
|------|------|
| 1 对 1 加密 | Olm |
| 群聊加密与密钥轮换 | Megolm |
| 多设备 | 每台设备独立密钥，消息自动发给对方所有设备 |
| 设备验证与交叉签名 | 表情符号比对 / 二维码扫描，验证一次后信任对方所有设备 |
| 密钥备份 | 服务端加密备份 + 恢复密钥，新设备可解密历史消息 |
| 消息同步、已读回执、输入状态 | 协议内置 |
| 1 对 1 通话信令 | 在加密房间内传递 |

我们要做的：自己的界面、登录流程、推送接入、以及第二阶段的业务功能（商城、订单）。

选择 Matrix 而不是自己组装加密的原因：多设备同步、密钥备份、设备验证、群聊密钥轮换是加密系统最容易出错的部分，而且出错时不会报错，只会悄悄地不安全。一个人加 AI 实现这些并确认其安全，风险过高。

## 发布渠道

| 平台 | 方式 | 时间 |
|------|------|------|
| 网页 / PWA | 浏览器访问，可添加到主屏幕 | 第一版 |
| 安卓 | Capacitor 打包，APK 直接下载安装 | 第一版之后紧接着做 |
| iOS | Capacitor 打包，App Store，**排除中国大陆区** | 推后 |

iOS 大陆用户通过 PWA 使用。iOS 不上架中国大陆区的原因：App 备案需要国内主体和接入商、即时通讯需要相关资质、国区应用不能使用 CallKit，且端到端加密聊天应用已有被国区下架的先例。

## 第一版范围（MVP）

| 第一版 | 推后 |
|--------|------|
| 网页 / PWA | iOS App |
| 邮箱验证码登录 | 短信登录、绑定手机 |
| 好友（以 Matrix 私聊房间实现） | 群聊（协议已支持，界面推后） |
| 1 对 1 加密聊天：文字、图片、语音 | 阅后即焚 |
| 1 对 1 语音视频通话（页面打开时） | 后台来电、原生通话插件、群通话 |
| 设备验证、密钥备份与恢复 | 本地消息搜索 |
| 拉黑、举报、账号注销 | 商城、订单、收款码、后台管理 |
| 邮件离线通知（不含内容） | — |

**所有房间默认开启加密，客户端不提供创建未加密房间的入口。**

## 架构总览

```
┌──────────────────────────────┐
│ 客户端（网页 / PWA / Capacitor）│
│ React 界面                    │
│ matrix-js-sdk + Rust 加密 WASM │
└──────────────┬───────────────┘
               │ HTTPS（自己的域名）
┌──────────────▼───────────────────────────────┐
│ 香港 / 日本 VPS                                │
│ Caddy：前端静态文件 + 反向代理 + 证书            │
│ Matrix homeserver（关闭联邦）+ PostgreSQL        │
│ 认证服务（邮箱验证码）                           │
│ coturn：TURN 中继（含 443 端口 TURN/TLS）        │
│ 推送网关（第二步，转发到 APNs / 极光或个推）       │
└──────────────────────────────────────────────┘
```

第二阶段的业务后端（商城、订单）单独部署，见下文。

## 服务端

| 部分 | 选择 | 说明 |
|------|------|------|
| Homeserver | **Synapse**（候选，验证后定） | 功能最完整、文档最多。也有更轻量的 Rust 实现，但功能完整度需要逐项核对 |
| 数据库 | PostgreSQL | Synapse 正式部署要求 |
| 联邦 | **关闭** | 不与其他 Matrix 服务器互通，减少攻击面和元数据外泄 |
| 注册 | 只允许通过我们的登录流程注册 | 关闭开放注册 |
| 部署方式 | Docker Compose，或社区维护的部署脚本（如 matrix-docker-ansible-deploy） | 一个人运维，尽量用现成脚本 |
| 媒体文件 | homeserver 自带媒体存储 | 加密房间里的图片和语音在客户端加密后上传，服务器只存密文 |
| 数据保留 | 配置消息和媒体保留策略，定期清理日志 | 少存元数据 |

## 客户端

| 部分 | 选择 |
|------|------|
| 语言 | TypeScript |
| 框架 | React + Vite |
| Matrix SDK | **matrix-js-sdk**，加密使用其 Rust 加密模块（matrix-sdk-crypto-wasm） |
| 路由 | React Router（SPA 模式） |
| 客户端状态 | Zustand（Matrix 的同步状态由 SDK 管理） |
| UI | Tailwind CSS + Radix UI（shadcn/ui） |
| 数据校验 | Zod |
| PWA | vite-plugin-pwa |
| App 打包 | Capacitor（前端资源打包进 App，不远程加载） |
| App 密钥存储 | iOS Keychain、安卓 Keystore（用于保护本地加密存储的密钥） |

**不 fork Element Web**：它的代码量很大，且使用 AGPL 许可证。我们基于 matrix-js-sdk（Apache 2.0）自己写界面，更轻、更可控。

## 加密

### Matrix 负责的部分

消息加密、多设备、设备验证、交叉签名、密钥备份、群聊密钥轮换，见上文"核心决策"。

### 我们负责的部分

| 事项 | 做法 |
|------|------|
| 恢复密钥的产品体验 | 首次登录引导用户生成并保存恢复密钥，明确告知"丢失后历史消息无法恢复" |
| 设备验证的产品体验 | 新设备登录时引导用旧设备验证；对方设备变化时醒目提示 |
| 禁止未加密房间 | 客户端只创建加密房间，服务端配置默认加密 |
| 通知不含内容 | 邮件和推送只提示"有新消息" |
| 本地数据保护 | App 端用系统安全存储保护本地数据；网页端提示用户在可信设备上使用 |
| 传输安全 | 全站 HTTPS + HSTS；App 端证书固定 |
| 网页端代码完整性 | 严格 CSP、Subresource Integrity、公开每个版本的构建哈希 |

### 需要如实告知用户的限制

- E2EE 只保护内容，不保护元数据（谁和谁、何时通信）
- 设备端风险无法通过加密消除：第三方输入法的云输入、浏览器扩展、木马、设备被检查。应提示用户关闭云输入，并在后续提供阅后即焚
- 网页端代码由服务器下发，安全性弱于 App 端
- 对外宣传使用"端到端加密，服务器无法读取你的消息内容"，不承诺"绝对安全"
- **上线前做独立安全审查，审查通过前不对外宣传端到端加密**

## 通话

| 阶段 | 方案 |
|------|------|
| 第一版：1 对 1 | Matrix 1 对 1 通话（WebRTC P2P，信令走加密房间），通过 coturn 中继。媒体是 DTLS-SRTP 端到端加密，中继不解密 |
| 之后：群通话 | Element Call（MatrixRTC + LiveKit，支持 E2EE） |
| 第二步：后台来电 | Capacitor 原生插件：iOS 用 CallKit + VoIP 推送（非大陆区），安卓用全屏通知 + 前台服务 |

注意：

- 不使用 Google STUN（国内无法访问）
- 国内移动网络 NAT 严格，P2P 经常失败，**必须有 TURN**
- Matrix 生态正在把通话迁移到 MatrixRTC，旧的 1 对 1 通话方式的长期支持情况需要在验证阶段确认

## 推送与通知

| 渠道 | 方案 |
|------|------|
| 网页 | 国内基本收不到网页推送，只在页面打开时提醒 |
| 邮件 | homeserver 内置的未读消息邮件通知，**不含消息内容** |
| 安卓（第二步） | 自己写一个小型 Matrix 推送网关，转发到极光或个推（聚合厂商通道） |
| iOS（推后） | 推送网关转发到 APNs；来电用 VoIP 推送 |

## 登录

| 部分 | 方案 |
|------|------|
| 主要方式 | 邮箱 + 6 位数字验证码（不用登录链接） |
| 认证服务 | 候选：Matrix Authentication Service（MAS），或自建认证服务通过 JWT 登录 homeserver，验证后定 |
| 发信 | 阿里云邮件推送（SMTP），配置 SPF、DKIM、DMARC；邮件中文、简短、不放链接 |
| 防刷 | 按 IP 和邮箱限流 + 人机验证（阿里云验证码或 Cloudflare Turnstile，实测后定） |
| 短信（推后） | 阿里云短信，签名通常需要企业资质 |

### 旧系统用户

旧系统的消息是明文，且没有加密密钥，**不迁移到新系统**。新系统从空白开始；旧系统在过渡期内保持只读，提示用户注册新账号。

## 第二阶段：业务后端（商城、订单）

商城、订单、收款码、后台管理不属于聊天核心，第一版不做。第二阶段单独建业务后端：

| 部分 | 方案 |
|------|------|
| 后端 | Supabase（Postgres + RLS + Edge Functions），或在同一台 VPS 上自建 |
| 身份打通 | 业务后端与 Matrix 账号关联（具体方式在第二阶段设计） |
| 订单卡片 | 业务后端以机器人账号在房间内发送，或客户端根据业务接口渲染 |
| 支付 | 实物商品用微信、支付宝收款码；如果卖虚拟商品，iOS 必须用苹果内购 |

| 部分 | 选择 |
|------|------|
| 服务器 | 第一版一台香港或日本 VPS（带国内优化线路）：Caddy、homeserver、PostgreSQL、认证服务、coturn |
| 备份 | PostgreSQL 和媒体存储每日备份到另一个地区 |

| 代码规范 | ESLint + Prettier |

## Claude Code 工作规范

新仓库的 `CLAUDE.md` 应包含以下规则：

1. **不修改加密协议相关代码**。加密由 matrix-js-sdk 的 Rust 加密模块负责，客户端代码只调用其公开接口
2. **每个功能必须附带测试**，提交前在本地跑通；测试结果以实际命令输出为准
3. **一次会话只做一个功能**，改动保持小而集中
4. **合并前运行 `/code-review` 和 `/security-review`**
5. **CI 必须通过才能合并**
6. 涉及登录、权限、加密配置、服务端配置的改动，在提交说明中单独列出，由开发者本人复核
7. 不在代码、日志、提交记录中写入密钥、令牌、用户数据

## iOS 上架合规清单（推后执行）

- [ ] 前端资源打包进 App，不使用远程加载（`server.url`）
- [ ] 排除中国大陆区
- [ ] 举报、拉黑、用户协议（明确禁止违规内容）、公开联系方式

- [ ] 收款码只用于实物商品，审核备注里说明；虚拟商品必须用苹果内购

## 动工前需要验证的事项

以下任何一项不满足，都需要调整方案。建议开发前先做小型验证：

1. **matrix-js-sdk + Rust 加密 WASM** 在浏览器、iOS WKWebView、安卓 WebView 中能否完成：登录、加密聊天、设备验证、密钥备份与恢复
2. **Homeserver 选型与部署**：Synapse（或轻量实现）关闭联邦后的资源占用；从国内访问的延迟和稳定性（包括晚高峰）
3. **邮箱验证码登录**：MAS 或自建认证服务能否实现"6 位数字验证码"流程；阿里云邮件发到 QQ、163 的到达率和延迟
4. **1 对 1 通话**：matrix-js-sdk 的通话在国内网络下经 coturn 中继的效果；旧通话方式与 MatrixRTC 的现状
5. **安卓推送**：自建推送网关转发到极光或个推的可行性

注：Matrix 生态更新较快，以上组件的现状以验证时的官方文档为准。

## 备选方案

如果验证阶段发现 Matrix 方案不可行（例如 Rust 加密 WASM 在 WebView 中无法正常运行），备选为：

**Supabase + vodozemac 自行组装 E2EE**：Supabase 负责登录、数据库、实时消息和文件存储，客户端用 vodozemac（WASM）实现 Olm/Megolm，自行实现多设备、密钥备份和设备验证。

不作为首选的原因：多设备、密钥备份、设备验证需要自己实现并确认安全，对一个人开发的项目风险过高；且必须有专业安全审计。

## 未采用的方案

| 方案 | 原因 |
|------|------|
| 自研加密协议 | 容易出现安全缺陷。旧版 `app_crypto.js` 缺少前向保密、身份验证和多设备支持，不迁移 |
| fork Element Web | 代码量大，AGPL 许可证，定制成本高 |
| Expo（React Native） | Hermes 引擎不支持 WASM，加密模块难以跨端复用；网页端包体积大 |
| Next.js | SSR 对海外服务器没有好处，增加运维复杂度 |
| Magic Link 登录 | 在邮箱 App 内置浏览器中打开会导致登录状态错位，且更易进垃圾箱 |
| 开启 Matrix 联邦 | 增加攻击面和元数据外泄，与产品定位不符 |

## 风险提示

- 面向国内用户、服务器在境外的聊天服务可能被封锁，运营者也可能承担法律责任。**投入大量开发前建议咨询律师**
- Synapse 使用 AGPL 许可证：直接部署不受影响；如果修改其源码并对外提供服务，需要公开修改后的源码
- 一个人运维 homeserver：需要做好监控、备份和安全更新
- 用户丢失恢复密钥且没有其他已验证设备时，历史消息无法恢复
